# M0.7 — Runtime-Validated Sprint Extension

M0.7 is the first TrueRecall milestone that proves a genuinely new player behavior while the original game is executing in a Genesis emulator.

The proof build is generated by `tools/build/m07c_sprint_new_anim_row.py` from the canonical `True Lies (World)` ROM.

## Scope

The extension adds a held-input sprint overlay on Genesis button **Y**.

When Y is clear, both patched sites execute the retail logic path unchanged. When Y is held during movement, the patch:

- selects an independent sprint animation-row identity;
- uses a faster movement parameter pair;
- resumes through the existing retail movement/animation machinery rather than replacing it wholesale.

This is deliberately a narrow engine-extension proof, not final Total Recall movement design.

## Hook architecture

Animation hook:

```text
retail site      0x0083A6
trampoline       0x1FE000
```

Movement hook:

```text
retail site      0x009864
trampoline       0x1FE080
```

The trigger tests normalized Y input through the existing input word at `F6EC`.

Sprint movement parameters:

```text
0x0300
0x0280
```

Retail normal-path values used by the corresponding movement path are lower; the proof intentionally makes the difference large enough to measure unambiguously.

## Independent animation row

The retail common animation-direction table beginning at `0x013F32` is copied byte-identically to verified free ROM space at:

```text
0x1FB000
```

All six known absolute references are redirected to the relocated copy.

A new sprint-only base selector is added at:

```text
selector      0x1FF0
row address   0x1FCFF0
```

For the proof milestone, this new row deliberately clones the retail JLLBFR presentation bytes. The important result is that the sprint has an independently addressable ROM-resident animation row while retail row `0x00F2` remains untouched.

This is **not yet proof of original new sprite art/animation frames**. That is the next presentation-authoring step.

## Runtime test method

BlastEm was driven through deterministic frame scripts. Base and patch received identical menu progression and identical movement input.

For the dense movement comparison:

```text
frame 2100: LEFT down + Y down
screenshots every 2 frames
frame 2142: LEFT up + Y up
```

Camera displacement was measured by integer-registering the static upper environment strip (`y=5..74`) against the pre-movement frame. Alignment error for the selected shifts was zero in the measured sequence.

This avoids depending only on player-sprite pose, which intentionally differs during the sprint presentation.

## Runtime evidence — CONFIRMED

### Movement is genuinely faster

Observed background/camera displacement:

```text
frame        retail/base      sprint
2118              12 px         24 px
2124              21 px         36 px
```

The observed 37-pixel camera plateau in this test area is reached at:

```text
retail/base   frame 2136
sprint        frame 2126
```

Thus the patched path advances through the same world space measurably earlier under the same directional input.

The effect is not merely an alternate animation.

### Active M0.7C path reproduces the validated diagnostic path

At frames:

```text
2080, 2120, 2140, 2160, 2200
```

M0.7C output is pixel-identical to the earlier M0.7A diagnostic sprint build while Y is active.

This proves that relocating the common table and selecting the new `0x1FF0` row did not alter the already validated sprint behavior.

### Animation-table relocation is a runtime no-op

A dedicated build that only relocates the common animation-direction table is pixel-identical to the canonical runtime at all tested comparison frames.

This validates the six redirected references and the table-copy boundary in execution, not only statically.

### Fallback is preserved

With Y not held, gameplay rows `0..233` are pixel-identical to base at all tested comparison frames.

A few residual screenshot differences were confined to capture row `234` and disappear again at the final comparison frame. No gameplay-region divergence was observed.

## Milestone interpretation

M0.7 is therefore **COMPLETE as a runtime engine-extension milestone**:

```text
unused/extra input
→ isolated hook
→ new movement behavior
→ independent animation-row identity
→ execution in emulator
→ measurable behavior change
→ preserved fallback path
```

The stricter art-content goal remains open: the current sprint row reuses retail presentation data. The next presentation milestone should author genuinely new animation frames/pieces/chunks rather than clone a retail row.
